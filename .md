# Projeto: Bíblia Interlinear & Comparativa

> Documento de arquitetura (v2). Foco: dados, banco, distribuição e sincronização. A interface visual fica para uma fase posterior.

---

## 📌 1. Visão Geral e Objetivo

Aplicação de **Bíblia de estudo** disponível como **webapp e app mobile** (um único código-fonte), com foco em estudo profundo das Escrituras, funcionamento offline e conformidade com direitos autorais.

### Funcionalidades

| # | Módulo | Descrição |
|---|--------|-----------|
| 1 | **Leitura** | Leitura corrida da Bíblia em português, com troca de tradução. |
| 2 | **Comparação** | Traduções lado a lado (Bíblia Livre, Tradução Brasileira 1917, Almeida 1911 e futuras licenciadas). |
| 3 | **Interlinear** | Texto original palavra por palavra: AT em Hebraico/Aramaico (WLC/OSHB) e NT em Grego (SBLGNT/TR). |
| 4 | **Tokens e Morfologia** | Para cada palavra: forma, lema, transliteração, morfologia decodificada em português, código Strong. |
| 5 | **Léxico Strong (PT)** | Definição em português por código Strong (`H` Hebraico, `G` Grego), incluindo Strong estendido (ex.: `H1254a`). |
| 6 | **Concordância** | "Onde mais essa palavra aparece?" — todas as ocorrências de um Strong/lema. |
| 7 | **Tradução literal** | Glosa literal palavra por palavra alinhada ao original. |
| 8 | **Referências cruzadas** | Repositório de referências cruzadas (fonte bruta em `/dados`). |
| 9 | **Comentários bíblicos** | Comentários de reformadores (ex.: João Calvino, via CCEL) traduzidos para pt-BR, ligados a livro/capítulo/versículo. |
| 10 | **Cronologia** | Linha do tempo dos eventos bíblicos, ligada aos versículos. |
| 11 | **Geografia** | Lugares com coordenadas, ligados aos versículos e eventos (mapa). |
| 12 | **Anotações** | Notas, destaques e marcadores do usuário, sincronizados entre web e mobile. |

## 🧭 2. Princípio Central da Arquitetura

O projeto tem **dois tipos de dados completamente diferentes**, e a arquitetura nasce dessa separação:

| | **Conteúdo (Referência)** | **Dados do Usuário** |
|---|---|---|
| Exemplos | Textos bíblicos, tokens, Strong, xrefs, comentários, cronologia, geografia | Anotações, destaques, marcadores, preferências |
| Quem escreve | Só o pipeline ETL (eu) | Cada usuário |
| Muda com que frequência | Raramente (por versão de conteúdo) | O tempo todo |
| Volume | Grande (milhões de linhas) | Pequeno por usuário |
| Onde mora | **Arquivos estáticos** (SQLite no mobile / JSON no web) | **Firestore** |
| Funciona offline | Sim, sempre | Sim (cache do Firestore) e sincroniza depois |

**Regra de ouro:** conteúdo bíblico **nunca** vai para o Firestore. O plano gratuito permite 50 mil leituras/dia; um único capítulo interlinear tem ~500 tokens. Se cada token fosse um documento, ~100 capítulos lidos por dia (somando todos os usuários) esgotariam a cota.

### Tech Stack

| Camada | Tecnologia | Papel |
|---|---|---|
| ETL | Python 3 | Ler fontes, normalizar, carregar no DuckDB, exportar |
| Banco de build | **DuckDB** | Armazém analítico local; validação e geração dos artefatos |
| Banco no app (mobile) | **SQLite** (com índice remissivo gerado no build) | Conteúdo embarcado e offline |
| Conteúdo no app (web) | JSON por capítulo + cache (IndexedDB / Service Worker) | Download sob demanda |
| Backend | Firebase (Auth, Firestore, Hosting) | Usuários e sincronização |
| App | Um código para web + mobile (Flutter **ou** React Native/Expo — *a decidir*) | Interface |

### Por que DuckDB continua, mas só no build
DuckDB é excelente para o ETL (lê CSV/JSON/Parquet direto, SQL analítico rápido, tipos `LIST`/`STRUCT`), mas **não é o banco ideal dentro do app**: o suporte mobile é imaturo e SQLite é o padrão em iOS/Android e tem versões WASM para web. Portanto: DuckDB produz, SQLite/JSON entregam.

### Restrições do plano gratuito (Spark) que moldam a arquitetura
Conferir na página oficial de preços antes de cada fase — os limites mudam.

| Recurso | Limite aproximado | Consequência no projeto |
|---|---|---|
| Firestore | 1 GiB, 50k leituras/dia, 20k gravações/dia | Só dados do usuário; ler notas por capítulo, não por versículo |
| Hosting | 10 GB armazenados, ~10 GB/mês de transferência | Transferência é o gargalo do **web**; cache agressivo e arquivos compactados |
| Cloud Functions | Indisponível no Spark | Nenhuma lógica de servidor; tudo no cliente ou no build |
| Cloud Storage | Exige Blaze desde 2026 | Conteúdo estático vai no Hosting, não no Storage |

## 🔢 4. Identificação de Versículos

### ID Determinístico (mantido)

$$\text{verse\_id} = (\text{book\_id} \times 1.000.000) + (\text{chapter} \times 1.000) + \text{verse}$$

* Gênesis 1:1 → `1001001` · João 1:1 → `43001001`
* Comporta Salmos 150 e Salmo 119:176 com folga.
* **Bônus importante:** como os IDs são ordenados dentro do livro, **intervalos** (Jo 3:16–18) viram `verse_start` / `verse_end` e a consulta "o que cobre este versículo?" é um simples `BETWEEN`. Isso vale para notas, xrefs, comentários e eventos.
* `verse = 0` reservado para títulos/superscrições (ex.: títulos dos Salmos), se adotado.

### ⚠️ Problema que o esquema atual não trata: versificação
O texto hebraico (WLC/OSHB) **não usa a mesma numeração** das Bíblias em português. Exemplos:
* Malaquias 4:1–6 (PT) = Malaquias 3:19–24 (Hebraico)
* Joel 2:28–32 (PT) = Joel 3:1–5 (Hebraico)
* Salmos com título: o título é o v.1 no hebraico, deslocando a numeração.

Sem um mapeamento, o interlinear mostrará o versículo errado ao lado do português. **Solução:** definir uma versificação canônica (a das traduções em PT) e uma tabela `verse_map` que converte a referência de cada fonte para o `verse_id` canônico.

#### Referências cruzadas
```sql
cross_references (
  from_verse_id   INTEGER,
  to_verse_start  INTEGER,
  to_verse_end    INTEGER,             -- = to_verse_start quando não é intervalo
  votes           INTEGER,             -- relevância (OpenBible); pode ser negativo
  source          TEXT                 -- 'OpenBible.info'
);
```

**Fonte:** OpenBible.info (CC BY), arquivo TSV em `/dados`:
```
From Verse	To Verse	Votes
Gen.1.1	Prov.8.22-Prov.8.30	78
Gen.1.1	Rev.4.11	209
```
* Referências em **OSIS** (`Gen.1.1`, `1John.1.1`) → `books.osis_code` converte para `book_id` → `verse_id`.
* `To Verse` pode ser um versículo ou um intervalo `início-fim` (o intervalo pode atravessar capítulos).
* A versificação segue o padrão inglês; aplicar `verse_map` (esquema `kjv`) onde divergir do canônico PT.
* A linha de cabeçalho traz a atribuição e a data de download: guardar em `content_release.notes`.
#### Pipeline engatilhado (`/etl/xref`)

**Parâmetros** em `/etl/config.yaml` (valores iniciais provisórios, ajustar após a análise):
```yaml
xref:
  arquivo: dados/cross_references.txt
  min_votes: 10        # corte mínimo de votos
  min_keep: 3          # sempre manter as N melhores do versículo (se votos > 0)
  max_per_verse: 20    # teto por versículo
```

**1. Carga bruta**
```sql
CREATE OR REPLACE TABLE stg_xref AS
SELECT * FROM read_csv('dados/cross_references.txt',
  delim = '\t', header = false, skip = 1,
  columns = {'from_ref': 'VARCHAR', 'to_ref': 'VARCHAR', 'votes': 'INTEGER'});
```

**2. Conversão OSIS → verse_id** (intervalo `A-B`; sem hífen, início = fim)
```sql
CREATE OR REPLACE TABLE cross_references AS
WITH p AS (
  SELECT from_ref,
         split_part(to_ref, '-', 1)                                     AS to_a,
         coalesce(nullif(split_part(to_ref, '-', 2), ''), split_part(to_ref, '-', 1)) AS to_b,
         votes
  FROM stg_xref
)
SELECT
  fb.book_id * 1000000 + split_part(from_ref, '.', 2)::INT * 1000 + split_part(from_ref, '.', 3)::INT AS from_verse_id,
  ab.book_id * 1000000 + split_part(to_a, '.', 2)::INT * 1000 + split_part(to_a, '.', 3)::INT       AS to_verse_start,
  bb.book_id * 1000000 + split_part(to_b, '.', 2)::INT * 1000 + split_part(to_b, '.', 3)::INT       AS to_verse_end,
  votes,
  'OpenBible.info' AS source
FROM p
JOIN books fb ON fb.osis_code = split_part(from_ref, '.', 1)
JOIN books ab ON ab.osis_code = split_part(to_a, '.', 1)
JOIN books bb ON bb.osis_code = split_part(to_b, '.', 1);
-- depois: aplicar verse_map (esquema 'kjv') onde a versificação divergir
```

**3. Validação** (nada pode se perder na conversão)
```sql
SELECT (SELECT count(*) FROM stg_xref) AS bruto,
       (SELECT count(*) FROM cross_references) AS convertido;   -- devem ser iguais
SELECT DISTINCT split_part(from_ref, '.', 1) AS livro_sem_codigo
FROM stg_xref WHERE split_part(from_ref, '.', 1) NOT IN (SELECT osis_code FROM books);
```

**4. Análise para calibrar os cortes**
```sql
SELECT quantile_cont(votes, [0.10, 0.25, 0.50, 0.75, 0.90]) AS quartis_votos,
       count(*) FILTER (WHERE votes <= 0)                     AS votos_nao_positivos
FROM cross_references;

SELECT quantile_cont(n, [0.50, 0.90, 0.99]) AS refs_por_versiculo, max(n)
FROM (SELECT from_verse_id, count(*) AS n FROM cross_references GROUP BY 1);
```

**5. Seleção para export** (aplica os parâmetros)
```sql
SELECT from_verse_id, to_verse_start, to_verse_end, votes
FROM (
  SELECT *, row_number() OVER (PARTITION BY from_verse_id ORDER BY votes DESC) AS rk
  FROM cross_references
  WHERE votes > 0
)
WHERE (votes >= $min_votes OR rk <= $min_keep)
  AND rk <= $max_per_verse
ORDER BY from_verse_id, rk;
```
O resultado já vem ordenado: o app mostra as primeiras e oferece "ver mais".

## 📦 6. Distribuição do Conteúdo

### Mobile
* O `biblia_vN.sqlite` vai **embarcado no app** (ou baixado na primeira execução).
* Busca textual pelo **índice remissivo** (tabelas no SQLite), 100% offline — ver seção 6.1.
* Módulos pesados e opcionais (ex.: comentários, segunda fonte grega) podem ser **pacotes separados** baixados sob demanda.

### Web
Conteúdo exportado como JSON compactado e versionado no Firebase Hosting:
```
/content/v{N}/manifest.json                      ← versão, hash e tamanho de cada pacote
/content/v{N}/texts/{translation}/{book}/{ch}.json
/content/v{N}/interlinear/{source}/{book}/{ch}.json   ← tokens + strongs do capítulo
/content/v{N}/lexicon/{H|G}/{bloco}.json              ← Strong agrupado em blocos
/content/v{N}/xref/{book}.json
/content/v{N}/commentary/{id}/{book}/{ch}.json
/content/v{N}/geo/places.json
/content/v{N}/chrono/events.json
```
* Cada capítulo baixado fica em cache (IndexedDB) e não é baixado de novo até mudar a versão.
* Alternativa a avaliar: SQLite em WASM no navegador, unificando a lógica de consulta com o mobile.
* Atenção ao limite de transferência mensal do Hosting: monitorar e, se o uso crescer, avaliar o plano Blaze ou uma CDN gratuita para os arquivos estáticos.

### 6.1 Busca — Índice Remissivo (web e mobile)

Gerado no build a partir de `verse_texts`, **o mesmo índice nas duas plataformas** (resultados idênticos no web e no celular).

**Normalização** (aplicada igualmente no build e na consulta): minúsculas, sem acentos (`Senhor` → `senhor`, `é` → `e`), sem pontuação. Sem radicalização na v1.

```sql
search_terms (
  term_id    INTEGER PRIMARY KEY,
  term       TEXT UNIQUE,      -- palavra normalizada
  doc_freq   INTEGER           -- em quantos versículos aparece (ordenar/ranquear)
);

search_postings (
  translation_id  TEXT,
  term_id         INTEGER,
  verse_id        INTEGER,
  positions       SMALLINT[],  -- posições da palavra no versículo (busca por frase exata)
  PRIMARY KEY (translation_id, term_id, verse_id)
);
```
| Plataforma | Formato |
|---|---|
| Mobile | As duas tabelas dentro do `biblia_vN.sqlite` (lista de posições serializada) |
| Web | Fatiado por tradução e prefixo: `/content/vN/search/{traducao}/{2 primeiras letras}.json`, baixado só quando a busca usa aquele prefixo e guardado em cache |

**Consulta:** normalizar o texto digitado → buscar cada palavra → interseção dos `verse_id` → (frase exata) conferir posições consecutivas.
**Busca nos originais:** não usa este índice; é a concordância via `token_strongs`.

## 👤 7. Modelo de Dados — Usuário (Firestore)

```
users/{uid}
  ├─ displayName, createdAt, settings { traducaoPadrao, fonteOriginal, tema... }
  ├─ notes/{noteId}
  │     verseStart, verseEnd, bookId, chapter,   ← bookId+chapter para consultar por capítulo
  │     text, tags[], createdAt, updatedAt, deleted
  ├─ highlights/{id}
  │     verseStart, verseEnd, bookId, chapter, color, updatedAt, deleted
  └─ bookmarks/{id}
        verseId, label, createdAt
```
### Estatísticas de leitura (versão simplificada — D7)
```
users/{uid}/stats/summary          ← um único documento por usuário
      totalMinutes                 tempo total de leitura
      byBook { "43": minutos }     → "livro mais lido"
      chaptersRead                 contagem de capítulos abertos
      lastPosition { verseId, translationId }  → "continuar de onde parei"
      activeDays, lastReadAt
```
* O app acumula localmente e grava **um resumo** ao sair do capítulo ou ao ir para segundo plano, com `increment()` e `merge`. Nunca uma gravação por versículo.
* Custo: ~1–3 gravações e 1 leitura por usuário ativo/dia; armazenamento de poucos KB por usuário. Muito abaixo das cotas do Spark.
* "Tempo de leitura" = tela de leitura em primeiro plano, com pausa após inatividade.
* Ficam para depois: versículo mais lido, histórico diário/mensal.
* **Privacidade (LGPD):** informar o que é coletado, permitir desativar e oferecer "apagar minha conta e meus dados".

### Consultas e regras
* **Leitura por capítulo:** `where bookId == X and chapter == Y` → uma consulta traz todas as notas do capítulo.
* **Exclusão lógica** (`deleted: true`) facilita a sincronização offline.
* **Persistência offline** do Firestore habilitada no web e no mobile.
* **Regras de segurança:** cada usuário só lê/escreve em `users/{seu uid}`.
* Notas referenciam versículos pelo `verse_id` canônico, então valem para qualquer tradução.

### Pipeline de comentários (D1)
```
fonte (CCEL: XML/ThML/HTML)
  → /etl/comentarios: extrair e dividir por trecho (verse_start/verse_end)
  → traduzir para pt-BR (status = 'máquina')
  → revisão manual (status = 'revisado')
  → commentary_sections no DuckDB
  → export por livro/capítulo
```
Só seções com o status mínimo definido (ex.: `revisado`) são exportadas para o app.

### Pipeline do léxico (D2)
```
STEPBible TBESH (hebraico) / TBESG (grego) — inglês
  → /etl/lexico: parse
  → traduzir para PT em lote (≈ 8.700 entradas H + ≈ 5.600 G no Strong clássico; o estendido tem mais)
  → lexicon_entries (source = 'STEPBible', license = 'CC BY 4.0', status)
STEPBible TAHOT (AT) / TAGNT (NT)
  → tokens + token_strongs + glosa EN → gloss_pt traduzida
```

## 🧩 12. Framework: React Native + Expo (decidido)

| Critério | Flutter | React Native + Expo |
|---|---|---|
| Web | Renderiza em canvas: seleção de texto, Ctrl+F e indexação por buscadores ficam limitados; carregamento inicial pesado | Gera HTML real (react-native-web): texto selecionável, Ctrl+F, leve, indexável |
| Mobile | Excelente, visual idêntico em todas as plataformas | Muito bom |
| Hebraico/Grego (RTL, sinais vocálicos) | Funciona | Funciona; no web usa o motor de texto do navegador (o mais maduro) |
| SQLite offline | `sqflite` (mobile); no web exige solução à parte | `expo-sqlite` (mobile; suporte web a verificar) |
| Firebase | FlutterFire, suporte oficial a web e mobile | JS SDK (web e Expo) ou React Native Firebase (nativo) |
| Linguagem | Dart (só se usa no Flutter) | TypeScript (serve também para web em geral) |

**Decisão:** React Native + Expo. O app é essencialmente de **leitura de texto**, e o web tem a mesma importância que o mobile.

### Camada de repositório de conteúdo
O app nunca consulta o banco diretamente: todas as telas usam uma interface única, e cada plataforma tem a sua implementação.

```ts
interface ContentRepository {
  getChapter(translationId: string, bookId: number, chapter: number): Promise<Verse[]>;
  getInterlinear(sourceId: string, bookId: number, chapter: number): Promise<Token[]>;
  getLexiconEntry(strongId: string): Promise<LexiconEntry>;
  getOccurrences(strongId: string): Promise<number[]>;          // verse_ids
  getCrossReferences(verseId: number): Promise<CrossRef[]>;
  getCommentary(commentaryId: string, bookId: number, chapter: number): Promise<CommentarySection[]>;
  search(translationId: string, query: string): Promise<SearchHit[]>;
}
```

| Plataforma | Implementação | Fonte de dados |
|---|---|---|
| iOS / Android | `SqliteContentRepository` | `biblia_vN.sqlite` embarcado, via `expo-sqlite` |
| Web | `JsonContentRepository` | JSON por capítulo no Firebase Hosting + cache em IndexedDB |

**Por que o web começa com JSON, e não com SQLite:** o suporte web do `expo-sqlite` ainda está em **alpha** e exige os cabeçalhos `Cross-Origin-Opener-Policy: same-origin` e `Cross-Origin-Embedder-Policy`. O primeiro desses cabeçalhos quebra o login do Firebase por **popup** (ex.: "Entrar com Google"). Com JSON, o web fica estável desde o início. Como as telas só conhecem a interface, trocar a implementação web por SQLite no futuro não exige reescrever o app.

**Busca:** índice remissivo gerado no build, igual nas duas plataformas (seção 6.1).

### Firebase no Expo
* Usar o **Firebase JS SDK** (funciona no web e no Expo), com persistência offline do Firestore.
* Login por **redirect** no web, se algum dia os cabeçalhos COOP forem necessários.
